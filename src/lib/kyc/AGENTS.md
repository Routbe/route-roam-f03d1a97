# KYC engine rules (src/lib/kyc)
- Provider results are reduced to `universal_nullifier = BLAKE3(Poseidon256(canonical_id) || pepper)` over the canonical ICAO/eIDAS anchors of `canonical-id.ts` (personal number first, then the document); Poseidon is the rout-zk x5_255_3 instance and `poseidon.test.ts` pins it to the Rust fixtures. Why: the same person yields the same value through every provider, and nothing stored can be turned back into a name or number.
- No name, document or personal number, date of birth, image or decision body is stored, logged or returned; the webhook re-fetches the decision from Didit and drops the body's `decision`, and the raw webhook body, Didit response bytes, canonical anchors and pepper copies are unpooled Node.js Buffers (`secure-buffer.ts`) zero-filled with fill(0), the anchors right after the nullifiers are computed and before any database call (tested; JS strings from JSON.parse cannot be wiped, so they are dropped right after reading). Why: zero-plaintext PII, and a forged webhook body can never define an identity.
- Didit webhooks are accepted only with a timing-safe HMAC-SHA256 over the raw bytes (X-Signature or X-Signature-Previous) inside a 300 s X-Timestamp window; the member comes only from the sealed `rk1.` vendor reference (`vendor-ref.ts`) and every write runs in that member's RLS context. Why: Didit never learns the member id and no caller can attest for someone else.
- The webhook consumes the session row last and every step before it is idempotent; transient failures answer 503 so Didit redelivers. Why: a crash between steps must not lose a paid verification.
- `rout_kyc_attest` (db/0288, live on Neon) is the only write path into `verified_identity_nullifiers`; the engine uses it when `hasSchemaFeature("0288")` and otherwise relies on the UNIQUE `identity_verifications.unique_human_id`. Why: a database still below 0288 keeps working, and from 0288 on another provider cannot attest the same person twice.
- DIDIT_API_KEY, DIDIT_WEBHOOK_SECRET, DIDIT_WORKFLOW_ID and the pepper (IDENTITY_HASH_PEPPER or PEPPER_SECRET, `pepper.server.ts`; when both are set they must be equal, else KYC is not configured) are read per call in server-only modules and never get a VITE_ prefix. Why: least-privilege secrets, and two peppers would split the nullifier registry.
- The Provider Discovery Hub lists providers from `providers.ts`; only entries with an `engine` can be started and their ids must exist in the 0288 provider CHECK (tested). Why: no button that does nothing, and the catalogue cannot drift from the database.
- Every `verified_identity_nullifiers` row names its evidence: `rout_kyc_attest` writes only `kyc_document` and refuses the zero-knowledge provider; the blue "KYC Attested" mark reads only `kyc_document` rows and the green "Real Human" shield only `zk_proof` rows, and `readPublicIdentity` ignores `real_human` until 0288 is live. Why: the owner keeps KYC and zero-knowledge humanity strictly apart; a liveness check never grants the green shield.
- Provider marks render only through `ProviderLogo` (src/components/icons/providers): inline vectors for the active engines, same-origin files in public/logos listed in `provider-logos.ts`, and the Building2 fallback when a provider has no mark or the file fails. Why: no third-party image request may reveal a visitor's IP, and an empty frame must never appear.
- Exception to the no-name rule (owner directive 2026-11-18): the document name (first_name/last_name, or the chip's given_names/family_name) is moved into unpooled Buffers, sealed with XChaCha20-Poly1305 under the ROUT_VAULT_KEK-wrapped profile field key into profiles.legal_*_sealed in the member's own context (`storeSealedLegalName`, via `afterAttest` before the session is consumed), and the Buffers are zero-filled; it is opened only for the blue-mark card (`openPublicLegalName`) and IBAN holder checks. Why: the card must show the attested name while Neon holds only ciphertext.
